## 1. 背景与目标

实施计划 01—04 已形成维修器材基础数据、事件与消耗模拟、确定性需求计算、场景推演、需求审查、预测诊断、可靠性参数校准、LLM 双模式接口、自然语言场景解析、工具编排、解释与报告生成能力。实施计划 05 的任务不是再建设一套独立应用，而是将这些能力以 WeKnora 原生专业模块的形式交付给企业用户。

本阶段在现有 WeKnora Vue 前端中新增“维修保障”一级入口，形成以下业务闭环：

```text
知识问答与任务描述
→ 场景草稿解析
→ 结构化场景确认
→ 多模型需求推算
→ 需求清单审查与版本发布
→ 库存缺口分析
→ 保障分配与库存预留
→ 领用、退回、调拨与盘点
→ 报告生成与追溯
```

系统继续保留 WeKnora 的知识库、文档解析、RAG、GraphRAG、通用问答、智能体和组织空间能力。维修保障模块与现有平台共享登录态、租户、角色、导航、主题和基础交互规范。

## 2. 设计原则

1. **WeKnora 原生集成**：不以 iframe、独立 Streamlit 或第二套前端框架作为企业主入口。
2. **结构化页面为主**：基础数据、正式场景、正式计算、库存操作、审查和报告均通过专业页面完成；聊天仅承担解析、检索、解释和导航。
3. **专业数值确定性**：需求数量、预测区间、保障率、库存余额、预留结果和版本状态只能由业务服务产生，不能由 LLM 直接生成。
4. **来源和版本可追溯**：关键字段、模型参数、人工调整、库存操作、审查建议和报告均绑定来源、版本和审计记录。
5. **租户完全隔离**：所有维修业务数据以 WeKnora `tenant_id` 为隔离边界。
6. **后端最终授权**：前端隐藏和禁用只用于改善体验，Maintenance API 必须执行最终权限校验。
7. **影响预览后执行**：库存、版本发布、规则发布和高风险修订必须先展示影响，再经用户确认执行。
8. **已发布对象不可原地覆盖**：场景、需求清单、保障方案、规则和报告通过新版本演进。
9. **成熟 EAM 思路、适度实现**：借鉴 IBM Maximo、SAP Asset Management 和 Oracle Maintenance 的器材、库存、预留、批次、序列号与维修任务关联模式，但不在本阶段引入完整 ERP、采购和财务体系。
10. **渐进交付**：本设计拆分为五个可独立验收的子阶段，每个子阶段同步完成页面、后端接口、数据迁移、权限和测试。

- 对 WeKnora 核心知识库、聊天或智能体架构进行无关重构。

## 4. 方案选择

### 4.1 方案 A：独立 Streamlit 应用

优点是开发速度快，适合算法实验；缺点是身份、租户、权限、导航、主题和部署分裂，难以形成统一企业产品。仅保留为后续科研批处理或调试工具，不作为 Plan 05 主方案。

### 4.2 方案 B：WeKnora 原生页面与后端代理

在现有 Vue 3、TypeScript、Pinia、Vue Router 和 TDesign 技术栈中新增专业模块，由 WeKnora 后端代理 `/api/maintenance/*` 请求并注入内部身份。该方案复用现有登录态和平台布局，业务边界清晰，适合长期维护。

**本设计采用方案 B。**

### 4.3 方案 C：iframe 或微前端嵌入

可降低前端代码耦合，但会增加鉴权交换、路由同步、主题一致性、弹窗层级、文件下载和故障排查复杂度。当前业务规模不需要独立前端运行时，因此不采用。

## 5. 总体架构

```text
浏览器
└── WeKnora Vue 前端
    ├── 原有知识库、问答、智能体、组织与设置
    └── 维修保障专业模块
        │
        │ HTTPS /api/maintenance/*
        ▼
WeKnora 后端
├── 验证现有登录态与空间权限
├── 生成 request_id
├── 签发短时内部 JWT
├── 代理普通 HTTP 请求
├── 代理 SSE 流
└── 统一错误映射与审计入口
        │
        ▼
Maintenance API
├── 内部 JWT 校验与租户上下文
├── 基础数据服务
├── 场景与版本服务
├── 需求计算与任务服务
├── 库存、预留、领退调拨与盘点服务
├── 审查和保障方案服务
├── AI 会话与快照服务
├── 报告服务
└── 审计与幂等控制
        │
        ├── maintenance-ai
        ├── 需求计算引擎
        ├── WeKnora 检索适配
        └── SQLite/PostgreSQL 业务数据库
```

### 5.1 边界

- WeKnora 前端负责交互、状态展示和用户输入，不直接访问 Maintenance API 部署地址。
- WeKnora 后端负责可信身份转换和反向代理，不承载维修专业业务规则。
- Maintenance API 是租户隔离、权限、事务、幂等、状态机和专业业务规则的最终边界。
- `maintenance-ai` 负责解析、推荐、解释和写作，不直接修改正式业务数据。

## 11. 库存管理

### 11.1 数量口径

```text
可用库存 = 当前库存 - 已预留数量 - 冻结数量
预计可用量 = 可用库存 + 在途数量 + 预计修复数量
净需求缺口 = 推荐需求量 - 预计可用量
```

界面必须同时展示账面库存、已预留、可用、冻结、在途、待修、预计修复、预测需求和净缺口，禁止使用单一“库存数量”代替全部口径。

### 11.2 仓库、库位和批次

普通器材按以下维度管理余额：

```text
租户 + 仓库 + 库位 + 器材 + 批次
```

批次记录生产日期、入库日期、失效日期、质量状态、冻结状态和数量余额。

### 11.3 序列号

关键件和可修件支持单件序列号追踪，状态为：

```text
在库
已预留
已领用
已装机
待修
在修
修复可用
报废
冻结
```

序列号可关联装备、安装位置、任务、维修记录、批次和库存流水。

### 11.4 有效期和出库策略

默认采用近效期优先：

```text
排除过期、冻结和不可用批次
→ 按失效日期由近到远
→ 同失效日期按入库日期由早到晚
→ 推荐出库批次
```

人工改选批次必须填写原因，并记录推荐批次和实际批次。

系统默认三级阈值为 180、90 和 30 天。租户管理员可以按器材类别配置，单个器材允许覆盖。风险等级根据当前日期动态计算，不固化在批次记录中。

### 11.5 库存操作

Plan 05 支持：

- 预留与解除预留。
- 领用。
- 未使用退回。
- 跨仓调拨。
- 冻结与解冻。
- 管理员库存修正。
- 库存流水查询。

每次操作必须先展示：

- 器材、仓库、库位、批次或序列号。
- 操作前数量、本次变动和操作后数量。
- 可用库存和需求缺口变化。
- 关联场景、清单、保障方案或任务。
- 对其他任务预留的影响。
- 风险提示和权限要求。

确认后由后端重新读取余额并在事务中执行。

### 11.6 权限

- `viewer`：仅查看库存、流水和风险。
- `contributor`：预留、解除预留、领用和退回。
- `admin`：增加跨仓调拨、冻结、解冻、库存修正、盘点确认和异常撤销。

### 11.7 盘点

```text
创建盘点任务
→ 选择仓库、库位、类别或器材范围
→ 保存盘点基准快照
→ 录入实盘数量
→ 计算账实差异
→ 填写差异原因
→ 管理员确认
→ 重新校验当前库存版本
→ 生成库存调整流水
```

盘点中不冻结整个仓库，但目标器材显示“盘点中”。若盘点期间发生业务变动，确认时必须提示冲突并重新计算差异，禁止覆盖新交易。

## 12. 任务场景

### 12.1 六步向导

```text
1. 基础信息
2. 装备构型
3. 任务条件
4. 可靠性与修理
5. 计算设置
6. 确认提交
```

每一步显示完成状态、缺失项、来源、风险和阻断项。高风险必填字段未确认时，不允许进入正式计算。

### 12.2 自动保存

- 字段变更后进行防抖自动保存。
- 同时保留“保存草稿”按钮。
- 草稿保存到 Maintenance API 的 AI 会话和快照，不仅保存在浏览器。
- 页面显示“保存中、已保存、保存失败、存在冲突”状态和最近保存时间。
- 离开页面前发现未同步变更时提示用户。

### 12.3 聊天到场景

```text
用户在问答中描述任务
→ AI 解析 ScenarioDraft
→ 保存 AI 会话快照
→ 返回 session_id
→ 跳转 /platform/maintenance/scenarios/new?session_id=...
→ 向导恢复字段及来源标签
→ 用户确认后保存正式场景
```

未确认草稿不写入正式场景事实，不参与正式需求计算。

## 13. 需求推算

### 13.1 引导式流程

```text
选择场景和版本
→ 预览装备、器材、可靠性、修理和库存输入
→ 推荐主模型与备选模型
→ 确认模型和关键参数
→ 并行执行
→ 查看进度和异常
→ 比较模型结果
→ 逐项选择或修订
→ 生成需求清单草稿
```

### 13.2 模型推荐

覆盖：

- 指数—泊松模型。
- 威布尔更新过程。
- 二项模型。
- 负二项模型。
- 蒙特卡洛模型。

推荐区展示：

- 推荐模型和推荐置信度。
- 数据完整度。
- 适用条件和关键假设。
- 参数来源。
- 主要风险。
- 备选模型差异。
- 不适用模型缺失条件。

用户可以切换模型。切换后重新校验参数，并保存系统推荐、用户最终选择、切换原因、推荐规则版本、模型版本和参数快照。

### 13.3 并行执行

- 默认执行主模型。
- 用户可勾选适用备选模型并行执行。
- 每个模型建立独立子任务。
- 单个模型失败不终止其他模型。
- 支持仅重算失败模型。
- 执行明细通过 SSE 推送；客户端使用 `session_id/task_id + last_event_sequence` 重连。

### 13.4 结果比较

统一比较：

- 推荐需求量、均值和中位数。
- 置信区间或预测区间。
- 缺件概率和保障满足率。
- 模型假设和参数来源。
- 计算耗时、随机种子和收敛状态。
- 器材级差异及差异原因。
- 与当前库存结合后的净缺口。

### 13.5 形成正式结果

选择一个模型作为清单基线。允许针对少量器材采用其他已执行模型结果或人工修订。

系统优先标记：

- 模型结果差异超过租户阈值。
- 预测区间重叠程度低。
- 关键件或高风险器材。
- 数据完整度不足。
- 老化或过度离散特征明显。
- 用户选择与系统推荐不同。

普通器材切换必须填写原因。关键件、高风险器材、数量下调超过阈值、超出全部模型预测区间或影响其他任务预留的修订进入管理员确认状态。

## 14. 需求清单与审查

### 14.1 状态机

```text
草稿
→ 待确认
→ 已确认
→ 已发布
→ 已作废
```

- 草稿可修改和重新计算，不参与正式保障统计。
- 待确认等待高风险修订和关键问题确认。
- 已确认内容冻结，可生成保障方案。
- 已发布成为当前有效版本，不可原地修改。
- 已作废保留历史和审计，不参与新业务。

同一场景允许多个历史版本，但只能有一个当前有效的已发布需求清单。新版本发布后，旧版本标记为被替代，而不是删除。

### 14.2 审查范围

- 数据完整性。
- 构型和器材适配。
- 配套件缺失。
- 数量比例错误。
- 互斥器材并存。
- 成套库存不齐。
- 共用器材重复计算。
- 替代关系不成立。
- 可靠性参数异常。
- 模型结果异常。
- 库存、修理和保障能力不足。
- 技术依据缺失、冲突或失效。

### 14.3 建议处理

支持逐条接受、拒绝、修改后接受、勾选批量接受和按问题类型批量处理。处理中只更新“待生成版本”，不实时修改正式清单。

点击“生成调整版本”时：

```text
检查未处理问题
→ 重新校验配套、比例、互斥和构型
→ 计算调整前后需求及库存缺口差异
→ 填写版本说明
→ 生成新需求清单版本
```

高风险问题未处理时允许保存审查草稿，但不能确认或发布。

## 15. 库存缺口与保障方案

### 15.1 生成流程

```text
读取已确认或已发布需求清单
→ 汇总仓库、库位、批次和序列号库存
→ 扣除冻结、过期和其他任务已预留数量
→ 应用近效期优先规则
→ 评估替代件
→ 评估在途和预计修复件
→ 形成建议分配与剩余缺口
→ 用户调整
→ 影响预览
→ 二次确认
→ 执行库存预留
```

保障方案独立于需求清单保存，库存变化不得反向修改已发布需求版本。

### 15.2 方案内容

- 原始需求、可用量和净缺口。
- 建议仓库、库位、批次或序列号。
- 原件和替代件数量。
- 已满足、部分满足和无法满足状态。
- 对其他任务和安全库存的影响。
- 临期、调拨、待修和在途风险。
- 人工调整和确认记录。

### 15.3 多任务竞争

当多个任务竞争同一器材时，先应用硬性规则，再计算综合评分。

硬性规则示例：

- 紧急任务必须优先。
- 指定保障等级不得降级。
- 关键器材不得突破最低安全库存。
- 指定任务必须保留最低保障量。
- 失效、冻结和构型不适用器材禁止分配。

综合评分因素：

- 任务保障等级。
- 任务紧迫程度。
- 计划开始时间。
- 器材关键度。
- 缺件影响。
- 当前保障满足率。
- 替代件可用性。
- 调拨、补给和修复时间。

系统生成推荐分配方案，用户确认后执行，不自动抢占库存。

### 15.4 优先级规则版本

租户管理员可配置权重和硬性规则。每个版本记录权重、归一化方法、适用范围、生效时间、修改原因和发布人。

规则修改后必须：

```text
编辑草稿
→ 选择历史或当前任务样本
→ 分别运行新旧规则
→ 比较分配数量、保障率、缺口、替代和安全库存
→ 识别受益、受损和异常任务
→ 管理员确认
→ 发布新版本
```

模拟不创建预留、不修改库存，也不改变已有方案。已生成方案继续绑定原规则版本。

## 16. 报告中心

报告类型：

- 需求推算报告。
- 模型比较报告。
- 需求审查报告。
- 库存缺口报告。
- 保障分配方案。
- 库存盘点报告。
- 器材风险报告。

每份报告保存报告类型、场景、需求清单版本、计算任务、规则版本、报告版本、引用、生成状态、生成时间、操作人和导出文件。

支持 Markdown、JSON 和 DOCX。重新生成时创建新版本，不覆盖历史报告。报告生成失败不影响计算、清单、审查或库存业务结果。

问答结果支持渲染：

```text

库存缺口卡

```

卡片允许跳转到结构化页面，不在聊天消息中直接执行高风险业务变更。

## 18. 身份、租户与权限

### 18.1 代理调用链

```text
浏览器携带 WeKnora 登录态
→ WeKnora 后端验证用户与当前租户
→ 生成 request_id
→ 签发短时内部 JWT
→ 代理到 Maintenance API
→ Maintenance API 验证 JWT
→ 建立用户、租户和角色上下文
```

前端统一调用 `/api/maintenance/*`，不得直接配置 Maintenance API 公网或内网地址。

### 18.2 内部 JWT

首版采用短时内部 JWT，建议有效期 3 分钟。claims 包含：

```text
sub
tenant_id
roles
aud
iss
iat
exp
jti
request_id
```

- 首版可采用 HS256 和独立内部密钥。
- `aud` 必须限定 Maintenance API。
- `iss` 必须限定 WeKnora 后端。
- Maintenance API 不信任请求正文或查询参数中的 `tenant_id`。
- JWT 过期时由 WeKnora 后端重新签发并重试一次。
- `jti`、时间窗和幂等键共同降低重放风险。

### 18.3 租户隔离

以下对象全部增加或验证 `tenant_id`：

- 装备、构型、BOM、器材和可靠性参数。
- 仓库、库存、批次、序列号和流水。
- 场景、计算、需求清单和审查。
- 保障方案、规则版本和模拟结果。
- AI 会话、消息和快照。
- 报告、导出和审计。

迁移要求：

- 对现有单租户历史数据执行显式归属迁移。
- 未归属数据不能默认暴露给所有租户。
- 唯一约束需包含 `tenant_id`，例如器材编码只在租户内唯一。
- 所有仓储查询通过租户作用域 Repository 或 Service 入口，不允许页面接口自行遗漏租户条件。

### 18.4 RBAC

| 能力 | viewer | contributor | admin |
|---|---:|---:|---:|
| 查看专业页面 | 是 | 是 | 是 |
| 下载报告与导出查询 | 是 | 是 | 是 |
| 新增、编辑、停用、导入主数据 | 否 | 是 | 是 |
| 创建场景和执行计算 | 否 | 是 | 是 |
| 处理普通审查建议 | 否 | 是 | 是 |
| 预留、解除、领用、退回 | 否 | 是 | 是 |
| 跨仓调拨和冻结 | 否 | 否 | 是 |
| 库存修正和盘点确认 | 否 | 否 | 是 |
| 高风险修订确认 | 否 | 否 | 是 |
| 优先级规则发布 | 否 | 否 | 是 |

## 19. 后端接口设计原则

### 19.1 路径

WeKnora 前端统一使用：

```text
/api/maintenance/v1/dashboard/*
/api/maintenance/v1/master-data/*
/api/maintenance/v1/scenarios/*
/api/maintenance/v1/calculations/*
/api/maintenance/v1/inventory/*
/api/maintenance/v1/reviews/*
/api/maintenance/v1/allocations/*
/api/maintenance/v1/reports/*
/api/maintenance/v1/ai/*
```

### 19.2 统一响应

普通响应包含：

```json
{
  "data": {},
  "meta": {
    "request_id": "...",
    "tenant_id": "...",
    "version": 1
  }
}
```

错误响应包含稳定错误码、用户可读消息、字段错误、冲突对象、request_id 和是否可重试。前端不依赖后端原始异常文本进行业务判断。

### 19.3 幂等

库存、发布、确认、导入和报告生成接口接收幂等键。相同用户、租户、业务动作和幂等键重复提交时返回原结果，不重复生成流水或任务。

### 19.4 乐观锁

可编辑和可执行对象包含 `version`。更新、确认和执行时提交预期版本。版本不一致返回冲突，不静默覆盖。

## 20. 实时任务与自动刷新

- 工作台采用 30 秒轮询。
- 需求计算、AI 编排和报告任务使用现有 SSE 能力展示详细进度。
- SSE 中断后按最后事件序号恢复。
- 服务器只重放缺失事件，已完成步骤不重复执行。
- 浏览器隐藏时暂停非必要轮询；运行中的 SSE 可根据浏览器策略保持或断线恢复。
- 页面卸载时释放定时器和连接。

## 21. 并发、一致性与审计

### 21.1 并发场景

- 预览后库存被其他任务预留。
- 盘点期间发生领用或调拨。
- 多人编辑同一场景草稿。
- 需求清单编辑期间产生新版本。
- 保障方案计算期间规则版本更新。
- 同一导入文件被重复提交。

### 21.2 控制方式

```text
数据库事务
+ 乐观锁 version
+ 幂等键
+ 执行前重新校验
+ 唯一业务约束
+ 审计流水
```

冲突响应必须返回当前版本、冲突字段和建议动作。前端提供重新加载、对比和重新提交，不自动覆盖。

### 21.3 审计

关键审计字段：

- tenant_id、user_id、roles。
- request_id、jti、幂等键。
- 业务对象、对象版本和操作类型。
- 操作前后摘要。
- 关联场景、计算、清单、方案或任务。
- 操作时间、结果和失败原因。

## 22. 异常与降级

| 异常 | 处理方式 |
|---|---|
| Maintenance API 不可用 | 页面进入只读或不可用状态，保留尚未提交的本地表单状态 |
| 内部 JWT 过期 | WeKnora 后端重新签发并重试一次 |
| 租户不匹配 | 拒绝请求并记录安全审计 |
| SSE 中断 | 根据最后事件序号自动重连 |
| 单模型失败 | 保留其他模型结果，允许仅重算失败模型 |
| Excel 部分错误 | 展示行级错误，不写入错误行 |
| 库存冲突 | 冲突行不执行，批量接口按设计返回逐行结果 |
| 报告生成失败 | 保留业务数据，允许重新生成报告 |
| AI 模型不可用 | 结构化场景、计算、库存、审查和报告模板流程继续工作 |
| 自动保存失败 | 显示未同步状态并允许手动重试，禁止误报已保存 |

- 工作台统计接口避免逐卡片请求，使用聚合接口一次返回主要指标。
- 大表格必须服务端分页，不一次加载全量库存流水或器材。
- Excel 导入、需求计算、报告生成和规则模拟使用异步任务。
- 30 秒工作台刷新不触发大规模明细查询。
- 前端在 1440×900 分辨率下完整可用，并兼容 WeKnora 现有侧栏折叠模式。
- 所有关键操作提供加载、成功、失败和可恢复状态，不允许点击后无反馈。

## 28. 验收标准

本阶段完成需同时满足：

1. 登录 WeKnora 后可通过原生左侧菜单进入维修保障模块。
2. viewer、contributor、admin 的前端能力和后端权限均符合矩阵。
3. 两个租户之间的全部维修业务数据完全隔离。
4. 器材页面具备成熟 EAM 所需的主档、适用关系、库存、批次、序列号、替代、配套和审计视图。
5. 场景可由问答生成草稿，并在六步向导中恢复、自动保存和确认。
6. 至少两个适用模型可并行运行，单模型失败不影响其他结果。
7. 需求清单支持审查、调整、高风险确认、发布、替代和作废版本。
8. 发布后的清单可生成保障方案，执行库存预留并形成完整流水。
9. 库存支持领用、退回、调拨、冻结和基础盘点，且并发冲突不产生负库存或覆盖新数据。
10. 优先级规则修改可以模拟新旧分配差异，模拟不影响正式库存。
11. 报告中心可生成并管理 Markdown、JSON 和 DOCX 版本。
12. AI 或外部模型不可用时，结构化专业业务仍可继续运行。
13. 前端、后端集成和端到端测试全部通过。
14. 无未处理的高风险租户越权、库存一致性或发布状态机缺陷。

## 29. 设计决策汇总

- 前端形态：WeKnora 原生 Vue 专业模块。
- 版本范围：标准版七页面。
- 基础数据：查询、新增、编辑、停用、Excel 导入导出。
- 导航：一个一级菜单和嵌套二级菜单。
- 工作台：租户实时数据，30 秒自动刷新。
- 身份：WeKnora 后端代理和短时内部 JWT。
- 租户：所有专业数据按 tenant_id 完全隔离。
- 场景：六步向导，API 会话快照自动保存。
- 需求推算：主模型推荐、备选模型并行和逐项结果决策。
- 清单：草稿、待确认、已确认、已发布、已作废。
- 库存：预留、领用、退回、调拨、流水和基础盘点。
- 批次：普通器材批次与有效期，关键件和可修件序列号。
- 出库：近效期优先，人工改选留痕。
- 替代：计算建议，用户确认后进入保障方案。
- 配套：自动审查，用户处理后生成新版本。
- 竞争分配：硬规则加综合评分，用户确认执行。
- 规则发布：先模拟影响，再发布版本。
- 报告：Markdown、JSON、DOCX 多版本。
