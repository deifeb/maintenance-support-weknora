# 基于 WeKnora 的维修器材需求管理系统多步详细实施方案

> 本实施方案依据《维修器材需求管理系统建设规划》进一步分解，面向当前仓库 `deifeb/maintenance-support-weknora`，以“先形成可运行闭环，再逐步增强算法、知识图谱和企业功能”为原则实施。

---

## 1. 实施目标

建设一套以 WeKnora 为知识与智能交互底座、以 Python 服务为专业业务核心的维修器材需求管理系统，最终形成以下完整闭环：

```text
维修资料与业务数据准备
→ 文档知识入库
→ 装备与任务场景配置
→ 构型、可靠性和维修关系查询
→ 需求推算
→ 库存核对
→ 缺口识别
→ 采购与调拨优化
→ 方案解释
→ 报告生成
→ 历史任务追溯与参数校准
```

第一版优先实现：

```text
任务场景输入
→ 装备构型和可靠性参数查询
→ 需求推算
→ 蒙特卡洛置信区间
→ 库存核对
→ 缺口清单
→ WeKnora 自然语言解释
```

## 3. 总体实施原则

### 3.1 不直接重构 WeKnora 核心

WeKnora 继续承担：

- 用户与权限；
- 知识库管理；
- 文档解析；
- 向量检索；
- GraphRAG；
- 智能问答；
- Agent 编排；
- MCP 工具接入。

维修保障业务能力放在 `extensions/` 中，通过 REST API 和 MCP 与 WeKnora 集成。

### 3.2 先单体、后拆分

第一阶段不立即建设复杂微服务，先形成一个可运行的 Python 业务服务；在接口稳定后，再将需求推算、配置优化和报告服务独立拆分。

### 3.3 先结构化计算、后大模型解释

需求数量、库存缺口和优化方案必须由确定性程序或数学模型计算。大模型只用于：

- 自然语言条件解析；
- 模型推荐说明；
- 检索知识；
- 调用工具；
- 结果解释；
- 报告撰写。

### 3.4 每一阶段必须可运行、可测试、可提交

每一个实施阶段都必须具备：

- 可执行代码；
- 最小测试；
- README；
- 示例输入；
- 示例输出；
- Git 提交记录。

## 阶段 0：业务需求确认与实施基线

### 目标

在开始编写模型和页面前，明确系统第一版到底计算什么、使用哪些数据、输出什么结果。

### 步骤 0.1：确定第一版使用场景

第一版只选一个明确场景，例如：

> 某型装备在给定装备数量、任务时长、任务强度和保障概率条件下，推算各类维修器材需求，并与现有库存进行核对。

需要明确：

- 装备是否同型号；
- 是否考虑多个任务阶段；
- 是否考虑预防性更换；
- 是否允许任务期间重复更换；
- 是否考虑修复后再利用；
- 是否包含低值消耗品；
- 结果按期望值还是保障分位数取整；
- 保障概率采用 90%、95% 还是可配置；
- 库存缺口是否考虑在途库存；
- 替代件是否计入可用库存。

### 步骤 0.2：定义第一版用户角色

建议定义：

| 角色 | 主要权限 |
|---|---|
| 系统管理员 | 用户、角色、模型、数据库和 MCP 配置 |
| 知识管理员 | 文档上传、知识库、图谱、标签和版本 |
| 业务管理员 | 装备、部件、器材和可靠性参数维护 |
| 需求分析员 | 创建场景、运行需求推算、查看结果 |
| 库存管理员 | 维护库存、仓库和在途信息 |
| 决策人员 | 查看需求、缺口、配置方案和报告 |
| 审核人员 | 审核参数、计算结果和配置方案 |

### 步骤 0.3：编写需求文档

创建：

```text
docs/requirements/
├── 01_业务需求说明.md
├── 02_用户角色与权限.md
├── 03_业务流程说明.md
├── 04_MVP功能范围.md
└── 05_验收指标.md
```

### 阶段交付物

- 《业务需求说明》；
- 《MVP 功能范围》；
- 《用户角色与权限》；
- 《业务流程说明》；
- 《阶段验收指标》。

### 验收标准

- 第一版输入字段全部明确；
- 第一版输出字段全部明确；
- 需求数量取整规则明确；
- 库存口径明确；
- 角色权限明确；
- 明确不纳入第一版的功能。

## 阶段 4：维修器材需求推算引擎

### 目标

建立独立、可测试、可解释的需求推算计算库。

### 步骤 4.1：统一计算输入

建议定义统一输入对象：

```text
equipment_id
equipment_quantity
mission_duration
mission_duration_unit
mission_intensity
environment_factor
support_probability
supply_cycle
allow_repeated_failure
model_type
simulation_runs
random_seed
```

### 步骤 4.2：统一计算输出

每个器材输出：

```text
spare_part_id
spare_part_name
model_type
expected_demand
recommended_quantity
variance
standard_deviation
lower_bound
upper_bound
support_probability
shortage_probability
parameter_sources
warnings
calculation_trace
```

### 步骤 4.3：实现参数校验器

校验：

- 装备是否存在；
- 装备数量是否合法；
- 任务时长是否合法；
- 构型是否完整；
- 部件安装数是否完整；
- 部件是否映射器材；
- 可靠性参数是否完整；
- 参数单位是否一致；
- 是否存在冲突参数；
- 模型是否适用。

### 步骤 4.4：实现指数—泊松模型

适用条件：

- 故障率近似恒定；
- 已知部件安装数；
- 已知任务时长；
- 故障事件近似独立。

实现内容：

- 期望故障次数；
- 泊松需求分布；
- 保障分位数；
- 推荐备件数量；
- 参数来源；
- 计算过程说明。

### 步骤 4.5：实现二项模型

适用条件：

- 每个安装件在任务期内至多失效一次；
- 已知单件任务失效概率；
- 安装数量明确。

实现内容：

- 单件失效概率；
- 总失效数量分布；
- 保障分位数；
- 推荐数量。

### 步骤 4.6：实现威布尔更新过程

适用条件：

- 部件存在磨损；
- 失效率随时间变化；
- 已知形状和尺度参数；
- 任务期内可能重复更换。

实现内容：

- 威布尔寿命采样；
- 更新过程模拟；
- 多次更换；
- 需求分布；
- 保障分位数。

### 步骤 4.7：实现负二项模型

适用条件：

- 有历史维修计数；
- 方差明显大于均值；
- 存在装备或任务异质性。

实现内容：

- 均值和离散参数估计；
- 需求分布；
- 保障分位数；
- 与泊松模型比较。

### 步骤 4.8：实现蒙特卡洛模拟

支持：

- 故障率不确定；
- 威布尔参数不确定；
- 任务强度不确定；
- 环境修正系数不确定；
- 多部件需求汇总；
- 缺件概率评估。

建议：

- 默认 10,000 次；
- 测试时使用 1,000 次；
- 固定随机种子保证复现；
- 大任务采用异步执行。

### 步骤 4.9：实现模型推荐器

规则示例：

```text
有威布尔参数且允许重复更换
→ 威布尔更新过程

只有任务期失效概率且单件至多失效一次
→ 二项模型

故障率近似恒定且历史数据少
→ 指数—泊松模型

历史计数方差显著高于均值
```
